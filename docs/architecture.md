# Architecture

```text
 Claude Code ──skills──▶ metarush CLI ─┐                       ┌─▶ MongoDB (Atlas or any) — metadata only
                                       ├─▶ internal/ops ──────┤    projects, assets, revisions, jobs, renders…
 Browser ◀──────────── local daemon ───┘   (one registry)      └─▶ Media store — Tigris/R2/B2/S3/GCS or a folder
   React dashboard      (127.0.0.1)                                 content-addressed originals, variants, renders
   + Remotion Player    ├─ HTTP: /api/ops/*, /media/*, uploads, SSE
                        ├─ worker: leases jobs (proxy, thumbnail, contact sheet, peaks, mezzanine,
                        │          evidence, transcribe (+ speakers), diarize, visual (Mac), describe,
                        │          render, qa)
                        └─ watched inbox
 Local cache (per installation, content-addressed, verified by SHA-256, never authoritative; the daemon keeps it under
 cache.maxGB without evicting pinned or in-use objects; `sync status` compares it with the canonical store)
```

## Process model
- **One binary** (`cmd/metarush`): CLI commands, `serve` (daemon = dashboard server + worker + watcher),
  `worker start` (headless worker, e.g. a Mac mini), `dashboard` (starts the daemon if needed and opens a
  one-time sign-in link).
- The **CLI runs operations in-process** against MongoDB and the media store. Long work becomes **jobs**.
- **Workers coordinate only through MongoDB**: atomic find-and-modify leases (45 s, extended by heartbeat), retries
  with exponential backoff, idempotency keys, recovery when a worker dies, capability matching (job types the
  machine can actually run; laptops on battery decline heavy jobs). A worker that stops while a job runs (the
  daemon shutting down, a terminal's `--wait` ending) releases it: back in the queue, the attempt not counted, never
  failed (`Queue.Release`). A terminal that runs jobs itself because no worker is online leases only the jobs it
  waits for (`Queue.LeaseAmong`), so follow-up work such as a render's automatic quality check waits for a worker.
  It keeps them to the end: a try that fails and will be retried goes back in the queue for a short wait
  (`jobs.RetryBackoff`: 10 s, then twice as long) and the terminal takes it again when the wait is over; the wait
  (`waitJobsOpt`) starts the terminal's worker again if it stops while a job it waits for still needs running, and
  ends with a plain error, never an endless wait, when it can't. A job no computer can run (this one lacks the
  component that brings it, and no other computer running MetaRush takes it) isn't waited for: the wait finishes the
  rest and ends with what waits and the component that adds it (`waitingErr`, `E_TOOL_MISSING`, exit 6; the command
  that adds it in `details.command`, each waiting job in `details.waiting`).
  The record a job works on is saved before the job is queued (`render.submit` saves the render with the job ID it
  chose, then queues the job), so the fastest worker always finds it; a job that still finds nothing goes back in
  the queue for a moment, a few times, saying why (`Queue.Postpone`: the attempt not counted), then fails plainly.
- The **dashboard assistant** (`internal/assistant`) holds conversations with the person's local Claude Code: one
  long-lived `claude -p` per conversation (stream-json on stdin/stdout), started from the daemon in
  `<home>/assistant/workspace` (skills, strict allowlist; the read-only `metarush` shim in `<home>/assistant/shim`,
  reached only through PATH) and resumed with `--resume` under the same flags. It only writes proposals (checked edit plans, render requests) and asks for changes, which become
  action cards; people apply both through the ops endpoint. Conversations live in MongoDB
  (`assistant_conversations`); the stream reaches the browser over SSE
  (`/api/assistant/conversations/{id}/events`, resumable with Last-Event-ID).
- The **dashboard** never talks to MongoDB or the bucket directly. Live updates arrive through Server-Sent Events
  fed by MongoDB change streams (polling fallback), so an edit made from Claude Code on another machine appears
  immediately. Notifications, QA reports, to-dos, voices and people are watched too; uploads, settings and Claude Code
  conversations are local events.
- **Activity** (`activity.summary`) is computed from server state on every request: browser upload records,
  ingest sessions, derivative jobs grouped per file, speaker detection runs, renders, QA and Claude Code conversations, each
  with a stage, progress, rate/ETA, machine and, for anything queued, the reason it waits (`jobs.Why`: battery, no
  machine, big jobs off, busy, retry backoff). The activity bar, the home page, the upload tray, `metarush activity`
  and per-clip status chips all read it, so a reload or another machine shows the same picture. Finished clips carry
  their open questions (`todos.AboutClip`: "2 questions about this clip" and a link to the To-dos page filtered to
  the clip), the same words and link job details and the bell show.
- **Notifications** are per-person documents with a group key (one "file ready" per asset, one battery notice per
  episode, one per speaker detection someone asked for); `Refresh` upserts re-mark a notification unread only when
  its content changed. `notification.list` adds the live count of open questions about the clip.
- **Battery policy** (`internal/power`): a worker reads the battery (`pmset`/sysfs) and defers heavy job types while on
  battery below `worker.heavyBatteryThreshold` (default 25, 0 = never). The lease query skips them unless a job
  allows it (`job.expedite`, "Process now"); the device document publishes the reading and reason; a restart
  continues the same deferral episode.
- **Catching up after upgrades** (`internal/catchup`): when a release adds an analysis, footage imported before
  it gets it too. Each step has a name and a version; the version a workspace completed is recorded in `catch_ups`
  (one document per workspace and step), and a step runs again only when its version goes up. The daemon runs the
  registry in the background when it starts, and `metarush migrate` at its end (its JSON has `catchUp`). Steps are
  idempotent (job idempotency keys, group-keyed questions), so machines starting together do no double work; a
  failed step is retried at the next start. Today: `voice-profiles` v1 (rebuild every person's voice from confirmed
  voices), `speakers` v1 (queue `diarize` for clips with audio and a finished transcript but no speaker detection;
  battery policy and activity bar as usual, the bell when voices are found), `questions` v1 (`todos.sync` every
  project: brief, ready to approve, music rights), `visual-changes` v1 (evidence again for clips analyzed before
  visual change detection) and `visual-index` v1 (the on-screen index for clips not looked at yet; only on a machine
  that can run it: elsewhere it returns `ErrNotHere`, is not recorded and reports nothing, so a Mac does it later)
  and `face-questions` v1 (group every clip's unnamed faces and ask once per person, folding the per-appearance
  questions earlier versions asked).
  A new backfill is a new step (or a version bump), not a migration.
- **Hot reload**: the daemon polls `config.yaml` and applies `worker.watch` (a `WatchManager` swaps the watcher),
  the battery threshold and the log settings without a restart; `config.SetField` edits one YAML node (comments,
  `${VAR}` and keychain references survive).
- **Activity log** (`internal/logbook`): `ops.Call` wraps every operation (start, end, the audited changes
  it made) and puts a scope in the context, so what the call causes — program runs (`tools.Set.OnRun`), job events
  (`jobs.Queue.OnEvent`, including jobs the call runs itself), ElevenLabs requests (the provider client reports
  each one) and audit events — links to its entry. The worker scopes job execution the same way; the assistant
  manager records Claude turns, cards and conversation lifecycle; skill tests record their cases. Entries are queued
  in memory, redacted and written in the background (one insert batch per second), spooled to
  `<home>/state/log-spool` when MongoDB is unreachable and flushed by the next process or the daemon. The daemon
  also counts dashboard reads into 5-minute summaries, stores Claude Code terminal turns the opt-in hook finished
  (`<home>/state/claude-hooks`), refreshes the hook's secret fingerprints and provider keys hourly, and applies
  `log.retentionDays` when set. Readers (`log.*` ops, the Log page, `metarush log`) describe entries in plain words
  with current names; `improve.*` turns them into improvement ideas.

## Ingest state machine
`probe (by content) → hash → dedupe (unique workspace+sha) → asset staging → resumable upload → verified →
cache adopt → available → derive jobs`. Interrupted ingests keep their session (upload ID, parts) and resume.

Browser uploads first ask `asset.precheck`: the dashboard fingerprints each file with WebCrypto (`fp1` = SHA-256 of
the first and last MiB, `sp1` = SHA-256 of 16 evenly spaced 64 KiB chunks), the server compares candidates of the
same size (computing fingerprints of older assets on demand with ranged reads) and finds duplicates within the drop
and interrupted uploads to resume. Stages `sending → checking → fingerprinting → storing → processing → ready` are
persisted in the upload record, so a reload rebuilds the tray from the server. The full SHA-256 stays authoritative.

## Picture and sound at cuts
```text
spec clips + transitionIn ──Timeline──▶ picture: from / durationInFrames / transitionIn / transitionOut
                    │                      (narration anchors resolve against this)
                    └──resolveSound (+ asset durations, transcripts, speakers)──▶ sound windows:
                         where each clip's sound starts and stops (lead / carry / auto / blends),
                         what the switch does to words (CutReport) ──▶ mixer envelopes, ducking ranges,
                         captions, QA's expected speech, edit-check warnings, QA findings
```

## Edit lifecycle
`plan (spec or ops) → edit check (schema + semantic preflight + diff + confirm token) → edit apply (immutable
revision, CAS on branch head, auto-rebase for disjoint ops) → revision.plan (RenderPlan) → render job → verified MP4
in the media store → dashboard → qa job (decode, measure, frames; report in `qa_reports`) → a person approves →
deliver (local, verified copies + sidecars)`.

Cut sheets are another way into the same lifecycle: `cut show` prints a revision as Markdown; `cut check` parses it
(strictly; problems point at a line and column), resolves quoted words to exact times, turns the difference from
its base revision into the smallest ops plan (`editspec.DiffOps`) and runs that through `edit check`; `cut apply`
then saves it like any ops plan (confirm token, locks, CAS, auto-rebase or `E_REVISION_CONFLICT`). Project folders
(`project checkout`) keep `cut.md`, `footage.md` and `.metarush/lock.json` (base revision and file hashes) so
`project status/pull/push` can tell local edits from new versions saved elsewhere. That lock file is also the
marker every guard uses to keep shareable data out of a project folder (`secretpath.ProjectFolder`: log exports,
bug reports and improvement exports refuse to write inside one).
