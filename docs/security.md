# Security model

**V1 deployment model: one team per database + media store, trusted collaborators.** MongoDB credentials authorize at
database granularity; they cannot enforce per-workspace isolation between hostile tenants. Teams that share a
cluster with untrusted parties need separate databases and credentials.

## Implemented controls
| Area | Control |
|---|---|
| Secrets | Stored in the OS keychain (namespaced per installation home) or env vars; never written to `config.yaml`; `doctor` fails if a URI with credentials appears there; URIs are redacted in all output. File-based secrets are never kept in sync folders or where git would commit them (see below). |
| Browser | Dashboard binds 127.0.0.1; Host-header allowlist defeats DNS rebinding; one-time sign-in nonces (10-min expiry) → HttpOnly SameSite=Strict session cookie; mutating requests need `X-MetaRush-Client`; no DB or storage credentials ever reach the browser (presigned, short-lived object URLs only); `X-Frame-Options: DENY`, `nosniff`, no referrer. Other computers come in only through `tailscale serve` on loopback ([remote access](#remote-access-over-tailscale) below). |
| Media | Content sniffing via ffprobe (extensions ignored); content-addressed, validated storage keys (no traversal); upload size limits; originals immutable; downloads verified by SHA-256. The media endpoints' memory of clips and renders (`internal/playback`) answers only after the Host check and the sign-in, only within its workspace, only when the database didn't answer, and with the same rules as the database's answer; it never holds a clip in the Trash, forgets one the database says is gone, follows every change the dashboard hears of, and lives in the daemon's memory only (an hour at most). GCS: only the *path* of a service-account key is stored (or ADC is used; `doctor` warns on a world-readable key file); resumable-session URIs (a week-long write capability for one object, bounded by declared checksums) are kept in the ingest session but never printed, returned by ops or sent to the browser, and the OAuth token is only sent to session URIs on the store's own endpoint. |
| Execution | Only allowlisted binaries (ffmpeg, ffprobe, node, whisper-cli and whisper-server from the same build, sherpa-onnx, nvidia-smi for one fixed query at studio setup, say/espeak-ng for the scratch voice, claude for the dashboard assistant, yt-dlp for link imports, deno for its version, brew only to update yt-dlp, git and gh to fetch and describe GitHub repositories, d2 to draw diagrams, pdftoppm/pdfinfo/sips for PDFs and pictures, the person's own rclone to read a Google Drive folder, below) with typed arguments — no shell, no model-supplied command text. AI supplies vetted template IDs and validated params, never code — except project-local motion graphics behind content addressing, an import allowlist, browser-only rendering and human approval per hash; vetted templates remain the default and the safe path. Every render page runs in a network jail with per-frame, total and bundle-size limits ([project motion graphics](#project-motion-graphics) below); child process groups killed on cancel. |
| Edits | Immutable revisions; optimistic concurrency; locks; HMAC-bound confirm tokens; `revision approve` is human-only. |
| Prompt injection | Skills treat footage, transcripts, captions, filenames, repositories and web pages as data ([below](#repositories-and-web-pages)). Tools return structured data; nothing in a transcript, a repository or a page is ever executed. |
| Audit | `audit_events` records ingest, revision creation/approval, renders, job control, reconcile — with user, installation and channel (cli/dashboard/worker/watch). Raw transcripts and secrets are not logged. The activity log (below) records more, redacted before writing. |
| Data safety | Migrations are additive. Nothing in MetaRush drops a database except the test suite, which only drops `metarush-test-*` databases on localhost. Uninstalling never deletes media. |

## Where secrets may live
People keep MetaRush homes, projects and footage on shared drives and inside git repositories, so secrets are
stored only where neither git nor a sync client can pick them up (`internal/secretpath`):

| Rule | Detail |
|---|---|
| Keychain first | Every secret (database URI, storage secret, provider API keys) goes to the OS keychain by default, namespaced per installation home. Keys are per machine: each machine sets its own. |
| One file-based mode | `--secrets env` keeps secrets in `METARUSH_*` variables, optionally from `<home>/.env` (0600). That file — and every other credential file MetaRush writes (join bundles from `machine invite`, the CI dotenv from `machine ci-key`) — is checked **before it is written or used**. |
| Sync folders: never | iCloud Drive (`~/Library/Mobile Documents`), `~/Library/CloudStorage/*` (Google Drive, OneDrive, Dropbox, Box), `~/Dropbox*`, `~/Google Drive`, `~/OneDrive*`, `~/Box*`, `/Volumes/GoogleDrive*` (symlinks are resolved). Refused with no override; a secrets file found there is not loaded (rotate it — it may already be uploaded). |
| Git work trees | Detected by walking up for `.git` (directory or file) or `git rev-parse`. A path git would commit (not ignored, or tracked) is refused. A path git ignores (`git check-ignore`) is refused for writing unless `--allow-unsafe-secret-path` is given; an existing ignored `.env` is loaded and `doctor` warns. |
| Defense in depth | Every installation home carries a `.gitignore` containing `*` (written by `init`/`join`, restored on load). Secret files are created 0600. Join bundles and CI dotenv files default to `~/.metarush-bundles/` (0700), never the current directory; `machine join` deletes the bundle after a successful join (asks in a terminal; `--keep-bundle` keeps it). |
| `doctor` | Fails a home or secrets file inside a sync folder or where git would commit it, a `.env` git does not ignore, and plaintext credentials in `config.yaml`; warns on loose permissions (`.env`, `state/confirm.key`, `state/sessions.json`, `state/providers.json`), a missing home `.gitignore`, and stray join bundles / credential dotenv files in the home, `~/.metarush-bundles` or the repository it runs in (with paths). |
| Repository guard | `scripts/secret-scan.sh` (CI job `secret-scan`) fails on likely secrets in tracked or staged files: MongoDB URIs with `user:password@`, Tigris `tid_`/`tsec_` keys, AWS access keys and secret assignments, `sk_…` API keys (ElevenLabs, Stripe), `xi-api-key` assignments, Google API keys (`AIza…`) and `x-goog-api-key` assignments, and PEM private keys. It never prints the matched value. Documented placeholders go in `scripts/secret-scan.allow` (narrow regexes) or carry a `secret-scan: allow` comment. |

## Integration keys (ElevenLabs, Google Gemini)
API keys for outside services are **per machine**: each machine that uses a service sets its own key, and a
teammate's key never reaches your machine.

| Area | Control |
|---|---|
| Storage | OS keychain (namespaced per installation home), or `<home>/.env` in env mode under the rules above. Never in MongoDB, `config.yaml`, logs, audit details or any API response. `state/providers.json` (0600) keeps only the masked suffix, when the key was set and the last check result. |
| Entering a key (CLI) | `metarush providers set <name>`: hidden prompt in a terminal, `--key-stdin` (pipe), or the `METARUSH_<NAME>_API_KEY` environment variable. There is no flag that takes the key, so it never lands in shell history or the process list. The key is checked with the provider before it is saved (`--no-test` to skip offline). |
| Entering a key (dashboard) | Settings → Integrations sends the key once, in the body of a POST to the local daemon (signed-in session, `X-MetaRush-Client` CSRF header, Host allowlist). The page checks it first, keeps it only in component state (not the query cache or browser storage) and can never read it back: status responses carry `configured`, where it is kept and `••••` + the last four characters. |
| Audit | `provider.set`, `provider.test`, `provider.remove` and `provider.settings` are audited with machine, provider and outcome — never the key. |
| Network | The key is sent only in the provider's auth header to fixed provider hosts (ElevenLabs and its data-residency hosts; Google's `generativelanguage.googleapis.com` in the `x-goog-api-key` header, never in a URL, and only to the host the request goes to, so a download link elsewhere never gets it). `METARUSH_ELEVENLABS_BASE_URL` and `METARUSH_GEMINI_BASE_URL` may point only at those hosts or a loopback test server. Google Cloud (Veo) keeps a service account's key, not an API key: its private key never leaves this computer, and never goes into an ability's requests or a Remotion refresh's steps (`providers.NotLent`, checked when planned and again when run); a signed token request goes only to `oauth2.googleapis.com` (a key file naming another token endpoint is refused) and the hour-long token only to `us-central1-aiplatform.googleapis.com` in the `Authorization` header, kept in memory and hidden in the log; `METARUSH_VERTEX_BASE_URL` and `METARUSH_VERTEX_TOKEN_URL` accept only a loopback test server. D-ID's key (presenters) goes only in the Authorization header to `api.d-id.com` (`METARUSH_D_ID_BASE_URL`: that host or a loopback test server); its finished clips are downloaded from the link it gives without the key; it downloads a training take from a two-hour link to the stored bytes, which nothing logs. HeyGen's key (stock presenters) goes only in the `X-Api-Key` header to `api.heygen.com` (`METARUSH_HEYGEN_BASE_URL`: that host or a loopback test server); its clips are downloaded from its links without the key. Voice samples are fetched by the daemon and streamed to the dashboard (`GET /api/providers/{name}/voices/{voice}/preview`, session required); the browser never talks to the provider. |
| Spending | `voiceover estimate` before generating; per-project spending limits are enforced before each request (`E_BUDGET`); generations are cached by provider + model + voice + settings + text, so unchanged lines are never billed twice. Generated video is priced first and sent only with the price a person agreed to (`maxUsd`, `E_CONFIRM_REQUIRED` otherwise), against a project budget and a daily limit for the team that are reserved before sending and settled after ([generative video](#generative-video)). |
| Voices | A voice copy (`voiceover clone`) is human-only and meant for your own voice; the consent statement is recorded in the audit log. Anyone else's voice needs that person's recorded consent as an asset (`E_CONSENT_REQUIRED` otherwise). Synthetic narration is marked `aiVoice` in takes and delivery sidecars. |
| Tests | Masking, keys never returned or audited, CLI stdin/prompt paths and the base-URL allowlist are unit-tested against in-process fakes of the ElevenLabs and Gemini APIs (`internal/testutil/fakeeleven`, `fakevideogen`; the latter records any key that appears in an address); `web/scripts/integrations-e2e.mjs` and `web/scripts/generate-e2e.mjs` check that no daemon response, page or browser storage contains the key, and that the browser sends it only to check and save it. |

## Generative video
Generated shots ([generative-video.md](generative-video.md)) send prompts, pictures and short clips to
Google and bring back video that can show people. The controls are about money, likeness and what stays at Google.

| Area | Control |
|---|---|
| What leaves the machine | The prompt (and a look's fixed description), the frames or clips a request uses (a look's stills and up to three clips of 3 s or less, a frame to continue from), pictures from the resources library it names. Nothing else: no project data, transcripts or other footage. The request hash recorded with each generation covers the exact bytes (by SHA-256). |
| What stays at Google | Gemini's background mode needs the interaction stored, so right after downloading MetaRush deletes the interaction and every file it uploaded or Google made (`DELETE /v1beta/interactions/{id}`, `DELETE /v1beta/files/{id}`) and records whether that worked (`forgotten`). Beyond what the API can delete, Google's own terms for the paid tier decide what it keeps (for example for abuse monitoring) and how it may use requests; read them before sending real people's likeness. |
| Likeness | Only through an approved look with consent in force: a person's own statement, or someone else's recording of their consent, with scope, expiry and withdrawal; minors and public figures refused; names in prompts and faces in frames are checked before anything is sent (`E_CONSENT_REQUIRED`). Recording consent and creating, testing, approving or withdrawing looks are `HumanOnly`: never from the assistant, MCP or a script. |
| Never automatic | Only a person's request with the agreed price starts a generation; the dashboard assistant proposes a priced card a person presses, and `generate.configure`, looks and consent are never offered to it. A send that may have reached Google is never repeated (it may have been charged). |
| What comes back | Downloads are streamed with a size cap, probed with ffprobe (no extension trust) and hashed before `ingest.File`; the clip carries `Asset.Source` (platform `generated`) and the tag `ai-generated`. |
| Disclosure | Generated clips are flagged in the dashboard, the cut sheet, the quality check and every delivery sidecar, with a per-platform checklist; Google adds a SynthID watermark. |
| Records | `generations` are written once, part by part; they never hold a key. Activity-log entries for Gemini calls keep the method, path, status and size, never the key or bodies. |

## Activity log
MetaRush records what it does in `log_entries`: operations, jobs, program runs, ElevenLabs requests and
Claude turns. The log is useful precisely because it holds what people asked for, so its rules are about what is
hidden, where the words are kept and where log data may be written.

| Area | Control |
|---|---|
| Redaction | Before anything is written — database, media store, spool, exports, bug reports — exact secret values are replaced (configured database password and storage keys, secret-looking `METARUSH_*`/`*_TOKEN`/`*_KEY`… environment values, dashboard cookies and sign-in nonces, the confirm-token key, provider API keys reported by the providers registry whenever a process reads or saves one and gathered from it by the daemon every hour, values of secret-named fields in an operation's input), then credential patterns (URL passwords, AWS and Tigris keys, `sk_…` keys, bearer tokens, JWTs, private keys) and the values of secret-named fields and flags (`key`, `secret`, `token`, `password`, `authorization`, `cookie`, `credential`; not identifiers such as `storageKey`). Program runs keep arguments (redacted, shortened), never their output, and only the end of the error output when they fail. ElevenLabs requests keep what they did, status, size and characters billed — never the key, the text or the answer. |
| Prompts and replies | `log.prompts` decides. **`workspace` (default): anyone who can read the workspace's database — every machine's database user and every Atlas user with access — can read what people asked Claude and its answers** (long ones are in the media store under `ws/<ws>/logs/`). `local`: kept only in `<home>/state/log-bodies` (0600); nothing is kept when the home is in a sync folder or where git would commit it, and the log settings say so. `off`: not kept; entries still say that a turn happened, which tools ran and which changes were proposed and decided. Changing it is people-only (`metarush log configure --prompts …`, Settings → Log). |
| The dashboard assistant | Reading the log from Claude's read-only channel never returns other conversations' words (lists and entries leave them out and search skips them); `log export`, `log tail --follow` and `improve signals` are refused there. |
| Claude Code terminal sessions | Recorded only after `metarush log claude-hooks enable` (people only, never from the dashboard). The installer adds MetaRush's hook commands to the user's Claude Code settings after backing the file up (`settings.json.metarush-backup-<time>`), changes nothing else, is idempotent, and `disable` removes only MetaRush's entries. The hook runs in every Claude Code session but keeps a turn only when the session used MetaRush; it buffers in `<home>/state/claude-hooks` (0700/0600), hides configured secrets with salted fingerprints (it never reads the keychain), always exits 0 and never blocks Claude Code. |
| Where log data may be written | `log export --out`, `log bundle` (default: Downloads) and `improve export --out` refuse git repositories (even paths git ignores), cloud-sync folders and MetaRush project folders. A bug report is redacted again and scanned for anything secret-shaped before the zip is written; if something is found, nothing is written. |
| Retention and deletion | Entries stay until deleted. `log.retentionDays` (0 = keep) makes the daemon remove this machine's older entries hourly; `metarush log purge --before <date>` is people-only and asks for confirmation (dashboard: a styled dialog); long texts no other entry uses are removed with their entries. |
| Spool | Entries that cannot reach the database wait, already redacted, in `<home>/state/log-spool` (0600) and are written by the next process or the daemon. |
| Tests | A whole-database, media-store, spool and hook-folder scan finds none of the planted secrets after every kind of entry (including the spool and its flush), after narration through the fake ElevenLabs API (key refused, saved, used, pasted into a prompt) and in bug reports; test fixtures build fake secrets at run time. |

Residual risks: a secret in an unknown format that MetaRush never held (typed into a prompt on a machine that does
not have it, for example) is not recognized; with `log.prompts: workspace`, everything people tell Claude is as
readable as the rest of the workspace's database.

## Link imports
`metarush import <link>` and the dashboard's "Paste a link" download videos with yt-dlp.

| Area | Control |
|---|---|
| What runs | yt-dlp through `internal/tools`: typed options built by MetaRush (`--ignore-config`, so no user config file changes them), the link always after `--`, MetaRush's own ffmpeg and JavaScript runtime by path. Never `--allow-unplayable-formats`: copy-protected (DRM) video is refused. |
| Which links | Classified before anything runs: http(s) only, no credentials in the address, never this computer or the local network (`localhost`, private and link-local addresses, `.local` names), so a link can't make MetaRush fetch from inside your network. Playlists and channels import nothing unless asked (at most 200 videos). |
| Where it runs | Each import is a job pinned to the machine that asked (`jobs.Installation`): its network, and its browser sign-in when the person opts in. Another machine's worker never takes it. |
| Browser sign-in | Opt-in per import ("Use my browser's sign-in", `--browser-signin <browser>`). MetaRush passes only the browser's name (`--cookies-from-browser chrome`) and never `--cookies` (the only option that reads or writes a cookie file; `--ignore-config` keeps a config file from adding it); yt-dlp reads the cookies from the browser's own store for that run, in memory. MetaRush never reads, copies, stores or logs cookies, and never writes a cookie file. The browser choice is remembered per machine (`imports.browser`) only as the next suggestion; it is never applied without asking. macOS asks before yt-dlp may read Chrome's keychain entry; Safari needs Full Disk Access. |
| Updates | `metarush import --update-tools` (a person asking) runs `brew upgrade yt-dlp` (Homebrew, which may also update Python and Deno) or `yt-dlp -U` (the self-contained build); a pip install is left to the person. The daemon's weekly update, while no import runs, upgrades yt-dlp only: `brew upgrade --formula yt-dlp` with the dependents check off, and only when everything yt-dlp relies on is installed and current, otherwise it waits for a person (doctor warns); it never upgrades Python, Deno or other packages (`imports.autoUpdate: false` turns it off). Every run is in the activity log. |
| PO tokens | No PO-token provider plugin is installed or required. If you install one, yt-dlp loads it from its plugin folders and `doctor` names it. |
| What is kept | The clip's provenance: site, address, video ID, account name and handle, channel address, upload date, original title, the description shortened to 1,000 characters, the stated license, when and with which tool it was downloaded, and whether a browser sign-in was used. Partial downloads stay in `<home>/scratch/imports/<job>` for a retry and are removed when the clip is added (failed ones after a week). |

## Repositories and web pages
GitHub repositories and web page snapshots bring outside content into the library, and slides are
made from it. Threats: a repository or page that tries to run code on this machine, reach this computer or
the local network through MetaRush, fill the disk, or steer Claude with instructions hidden in its text.

| Area | Control |
|---|---|
| Nothing runs | A repository is never cloned into a working folder, built, tested or installed. git fetches one commit into a fresh bare repository in scratch with `core.hooksPath=/dev/null`, `core.fsmonitor=false`, every protocol but https off (`protocol.allow=never`), `transfer.fsckObjects`, no prompts (`GIT_TERMINAL_PROMPT=0`, a failing askpass, `credential.interactive=never`) and `GIT_LFS_SKIP_SMUDGE=1`; MetaRush then reads the blobs raw (`ls-tree -z`, `cat-file --batch`), so no checkout, filter, attribute, `export-subst`, hook or LFS program from the repository runs. Only text files are kept: NUL bytes, LFS pointers, links, submodules, odd names, files over `fileKB` and anything past `totalMB`/`files` are left out and listed. Unpacking refuses absolute paths, `..`, links and anything but plain files. |
| Pictures from a repository's folders | Only under paths a person names (cleaned: no `..`, `.git`, patterns or control characters). The same raw blobs, told by their bytes (an LFS pointer, a link, a submodule or an animated GIF is left out, never followed or downloaded), capped per picture (`pictureMB`) and per fetch (`picturesMB`, `pictures`, and reading stops at four times that); PNG, JPEG, WebP and GIF are only decoded by Go's image readers (huge pictures aren't decoded), SVGs are sanitized like any SVG, and each is stored by its SHA-256 with MetaRush's own provenance (`repo@commit:path`). |
| Sign-in | Private repositories work through the person's own credential helper (`gh auth setup-git`) and `gh` sign-in. MetaRush never asks for, reads, stores or logs a token, never passes one in argv, and makes only read-only `gh api` GET requests. Addresses must name a repository on `github.com` (`owner/repo`, no credentials); the fetch itself is https only. |
| Reading | `resources path` unpacks a read-only copy (files 0444) under the cache, one folder per version; Claude reads it with Read, Grep and Glob. The dashboard assistant's read-only allowlist is unchanged. |
| Untrusted text | Skills ([safety.md](../skills/_shared/safety.md)) treat a README, comments, commit messages and page text as data: they never follow instructions found there, never run anything a repository says to run, never open links it contains, tell the person when a file or page tries to give orders, and leave anything that looks like a secret out of slides. The provenance people see is MetaRush's own record (`repo@commit:path:lines`, the address and the date), not what a repository or page claims. |
| Generated slides | Code is highlighted by Shiki in Node and escaped into a page MetaRush writes; diagrams are Mermaid with `securityLevel: strict` and SVG text labels (no HTML), or `d2 --bundle=false` behind a proxy that refuses everything; both are drawn in the render jail (refusing proxy, host-resolver rules, CSP, a bypass only for that run's loopback page server). Every SVG made or added is sanitized (no scripts, event handlers, `foreignObject` or outside references). |
| Snapshots | A fetch job on the machine that asked, outside the render jail but in a jail of its own: Chromium with a fresh, empty profile (no cookies, no sign-in) whose only way out is MetaRush's filtering proxy (`render/web/proxy.mjs`; loopback goes through it too). The proxy resolves every name itself and refuses loopback, private, link-local, carrier-grade NAT, benchmark, multicast and "this network" addresses — also inside IPv6 forms that carry them (mapped `::ffff:7f00:1`, compatible, NAT64, 6to4) — plus IPv6 unique-local, link- and site-local addresses and `localhost`, `.local`, `.internal` and single-label names; it connects to the address it checked, so a name can't change its answer in between. Redirects, frames, workers, WebSockets and pictures all go through it; plain-http upgrades are refused and a byte budget (400 MB) stops a page that downloads without end. WebRTC can't use UDP outside the proxy; downloads and dialogs are refused; each page has a time limit (`timeoutSec`, 45 s) and the run a total one. Go checks the address (and what it resolves to) before the browser starts. |
| What is kept | PNG pictures (the whole page at most `fullHeightK` thousand pixels tall), the readable text (shortened), title, description, site name, theme colour, language, and the preview picture and icon — downloaded with the same address rules (checked first, the connection to the address checked, no redirects, at most 5 MB, 20 s) and kept only when they are PNG, JPEG or WebP pictures. Depth 1 follows same-site links only, skipping sign-in, account, cart and file links, up to 20 pages. Nothing from a page runs again: the dashboard and renders show its pictures. Picture links (`resources add <picture address>`) download in Go with the same refusal checked at every connection, redirects included (at most 5). |
| Tests | Fixture repositories are built at test time (`scripts/make-fixture-repo.sh`, `METARUSH_GIT_BASE`, the only way `file://` is allowed); Go tests cover addresses, unsafe archive entries, binaries and LFS pointers left out, licences and the fetch from a fixture, and the pictures kept from its art folder (the `art` and `art-second` steps: told by their bytes, an SVG cleaned, what is left out and why, a newer commit). `node render/web/test.mjs` (in `npm run test:motion -w video`) shows the proxy and the small download refuse loopback by number, by name, by mapped IPv6 and by a name whose answer is local (a loopback sink sees no request), and that the byte and size limits hold. Snapshots of the local fixture site run only with `METARUSH_PAGES_ALLOW_LOCAL=1`. |

Residual risks: a page's own text and pictures can still say anything (they are shown, never run; credits and QA's
licence note help people check what they use); code on a slide is whatever its authors wrote, so people review
slides like any graphic; the snapshot browser reaches the public internet from the person's network address, like
their own browser would.

## Recipe files from another workspace
A recipe exported in one workspace is brought into another as a file ([recipes.md](recipes.md#between-workspaces)).
Threats: a file crafted to run code here, to slip code past an approval, to fill the disk or write outside its place,
to steer Claude with words in the recipe, or to carry someone's likeness or secrets across.

| Area | Control |
|---|---|
| Reading the file | A zip read strictly: only `recipe.json`, one sheet (never used) and `files/<sha256>`, stored or deflated; at most 200,000 entries; the description at most 32 MB and decoded with no unknown fields under a named format (`metarush.recipe-file/1`); every file it lists present at its size and nothing else; each file unpacked into a fresh scratch folder named by its SHA-256 (never a name from the file) and checked against it as it comes out, so a damaged or changed file brings nothing in. File names it gives are only suggestions, cleaned of folders and control characters; where it says a picture or clip came from (a site, a licence, a generated shot) is the other workspace's record, kept as its words, and what it says it left out is shown quoted as its own. The dashboard sends the file as a request body (signed in, the CSRF header, at most 8 GB) to a file MetaRush chose; `recipe.export` and `recipe.import` are LocalOnly, never on `/api/ops`. |
| What comes in | Pictures through the ordinary picture pipeline (told by their bytes, SVGs cleaned, HEIC converted), footage through the ordinary import (probed, hashed, never stored twice), each a thing of its own in one project; a generated shot stays flagged as generated, and one showing a real person is never exported (consent covers its workspace's projects). The document's references are rewritten to what came in; anything else that named the other workspace is taken away. |
| Code | Never trusted for having been approved elsewhere: motion graphics and shared libraries are kept by the hash of their canonical archive (parsed and checked first) with no record, so nothing can render them until someone checks them here (test frames in the jailed browser) and a person approves them (HumanOnly). A Remotion version must pass the import's own rules (another tool's settings, secrets by name or content, installed packages, git and odd names refuse it) and comes in as a new source whose packages no one has allowed, never read and never approved: a person allows its packages, it is checked in the jail, a person approves it. Bytes this workspace had already keep what people here decided. Nothing from the file runs during the import. |
| Words | The recipe's title, hints, rules, purposes and labels were written elsewhere: the version is a draft only a person makes current, its page says it came from another workspace, and the skills treat imported words as data, never instructions ([safety.md](../skills/_shared/safety.md)). |
| Tests | `internal/recipes/exportimport_test.go` (a round trip between two workspaces, lineage, names, a script entry, a damaged file, another format and a missing file refused with nothing brought in, graphics kept without a record until checked and approved, a Remotion version waiting with nothing allowed, one carrying another tool's settings refused), `internal/api/recipes_test.go` (sign-in, CSRF, the download, the upload, the ops refused over `/api/ops`), the acceptance run's step (two workspaces). |

## Ability files from another workspace
An ability exported in one workspace comes into another as a file ([abilities.md](abilities.md#between-workspaces)).
Read strictly: only `ability.json`, `archive.json`, `ability.yaml` and `notes.md`, each once and within its size;
the description decoded with no unknown fields under a named format; the archive canonical (re-encoded byte for byte),
its SHA-256 the version the file names, no keys or credential files in it, its manifest sound. It comes in
**imported**: its approval elsewhere is information only, it can't be approved until its test has run on a computer
here, and it is never set up. Words from the file (its workspace's name, owners' names and notes) are kept as data,
control characters removed. Nothing in it runs during the import.

## What may leave this computer ([what-may-leave.md](what-may-leave.md))
A client's Content Settings can keep their footage, voices, faces, words and pictures from AI services (by
provider), abilities (by host), Claude and AI apps (by the Claude account's terms), cloud storage and delivery. Every
place that sends something asks first: AI requests at the plan and again just before sending; ability runs at the
plan, before starting and request by request in the proxy; operations that show words or pictures on an AI's channel
(the panel, Claude Code in a terminal, MCP), with the panel's read rules denying the client's frames; footage added
to a cloud bucket and moves of the media there; videos and timelines written to sync folders; Recipes' files. Refusals
are `E_KEPT_HERE` and recorded (`leave.refused`); the receipt lists what left and where. Only people change the rules,
and letting more leave takes a person who is an owner — also by switching settings or moving a client's footage. On AI channels reads are denied by default: each says what it shows, and while any client keeps things from Claude the panel reads no shared frame or cache folder.

## Review links for people outside the workspace ([outside-reviewers.md](outside-reviewers.md))
Nothing new listens: a review page is a private, signed, expiring static page in the workspace's own media bucket,
under `review/<128 random bits>/`, and MetaRush only reaches out to read reviewers' comment slots back. Every address
in the page is a signed link to one object and one method until the link ends (at most 7 days: a store's signatures
stop there); comment slots take one signed PUT of exactly 128 KiB each (the signature covers the length and type).
The page carries no key and no address of MetaRush; its Content-Security-Policy allows only its own script and style
(by hash) and the bucket's address, sends no referrer and asks not to be indexed; reviewers' words are set as text.
Expiry is enforced by the store and again by MetaRush (it deletes the objects and stops reading them); taking a link
back deletes them at once, and slots written again through a still-signed upload are deleted on every look until the
signature ends and never read. Reviewers' words come in cleaned, within limits (8 browsers, 100 comments each, 60 an
hour per link, 2,000 characters, a 60-character name), as comments marked "(outside)", and reach an AI only quoted.
Making, re-sending and taking back a link are people's steps; owners decide who and for how long; What may leave
decides whose things may go. Tailscale Funnel stays refused.

## Google Drive through the person's rclone
A recipe input can read a Google Drive folder without syncing it ([recipes.md](recipes.md#a-google-drive-folder-as-an-input)).
Threats: MetaRush holding Google credentials, a folder's address that makes rclone read this computer's files or
another service, a file swapped between the plan and the run, and a test touching a real Google account.

| Area | Control |
|---|---|
| Sign-in | The person's own rclone and its own sign-in (`rclone config`); MetaRush never asks for, reads, stores or logs a Google token or rclone's settings, needs no Google Cloud project, and runs rclone with `--ask-password=false` (settings locked with a password are said plainly, never asked for). |
| What runs | Only the allowlisted `rclone` through `internal/tools` with typed arguments (`version`, `listremotes --long`, `lsjson --files-only --hash`, `backend copyid` into a file MetaRush chose in scratch; positional arguments after `--`). A folder is `remote:path` with a remote name rclone allows (no leading dash, no `:` or `,` — so no on-the-fly backends such as `:local:` and no connection-string options) that must be one rclone lists with the `drive` type; paths have no `..`, `.` or control characters. |
| What comes in | Only the files a run uses, by their Drive ID, each checked against the listing's size and Google's checksum (else refused: it changed) and capped (pictures 512 MB, footage 64 GB), then kept by content through the ordinary picture and footage pipelines. A plan's fingerprint covers each file's ID and checksum, so a file changed since a person saw the plan starts nothing. Names of Drive files are data. |
| Tests | Under `go test` the real rclone is refused unless `tools.rclone` points at a fake (`internal/drive`, as for Tailscale); `internal/testutil/fakerclone` plays rclone from local folders (expired sign-ins, missing remotes and folders, locked settings, no checksums); the acceptance run builds the fake and points `METARUSH_RCLONE` at it before anything starts. |

## Browser extension
The "Send to MetaRush" extension ([browser-extension.md](browser-extension.md)) talks to the local daemon at
`/ext/*` and never to the dashboard API.

| Area | Control |
|---|---|
| Pairing | A person makes a one-time code for their own browser (Settings → Browser extension, or `metarush extension pair` at the host, which asks in an interactive terminal and pairs for the owner; the op is people-only and refused on the assistant channel; anyone signed in; older versions: owners only). Each person's code waits on its own; codes are 8 characters from a 30-letter alphabet (about 39 bits), work once, for 10 minutes, burn after 5 wrong tries (a wrong code counts against every waiting code), and pairing attempts are limited to 10 a minute. |
| Whose it is | A pairing records the person who made the code: the videos, imports and page snapshots it sends are theirs. Every `/ext` request checks that person's account like a session check (`auth.MaySend`: cached 5 s, the last 10 minutes' answer when the database doesn't answer): turned off, removed, not yet joined, or any account but the owner's with "Just me" sign-in, and it is refused (403; the extension keeps its token, so it works again when the account is back). Pairings from before belong to the installation's owner. |
| Token | Pairing returns a random token (`mrx_` + 64 hex characters) once. The daemon stores only its SHA-256 (`<home>/state/browser-extension.json`, 0600, per machine) and compares in constant time. The token is bound to the extension origin that paired (`chrome-extension://<id>`); from any other origin it is refused. It never reaches the activity log (registered as a secret). |
| Scope | The token can only: say hello (the machine's name), start an upload (into the inbox), send bytes to and ask the offset of an upload that same browser started, ask for a link import, and, with the `pages` scope, send the page on screen as a web page snapshot (all answered in words, no IDs). Nothing returns clips, projects, jobs, resources, activity or settings. `/api/*` and `/media/*` need the dashboard session and refuse the token. Scopes are fixed when a browser pairs: one paired before "Send this page" keeps sending video only and is asked to pair again (403, `reason: scope`) instead of being widened silently. |
| Send this page | Only when the person clicks it in the popup. The extension asks for `activeTab` (no standing access to any site) and `scripting`, reads that one tab's address, title, description, site name, theme colour, language and text (`innerText`), and takes a PNG of what is on screen with `captureVisibleTab`. The daemon takes http(s) addresses only, never one on this computer or a local network or with credentials (the fragment is dropped), checks that the screenshot is a PNG (at most 18 MB and 12,000 pixels a side; the whole request 24 MB), shortens every text field (the text to 200,000 characters) and adds the page to the workspace library as a dated snapshot. Only http(s) tabs are sent (the browser's own pages are refused in the popup); where the browser doesn't let extensions read a page (the extension store), only the picture is sent. A page the person is signed in to is sent as they see it — that is the point — so the popup says it sends what is on screen. |
| Requests | Every `/ext` request must carry an extension `Origin` (web pages can't send one) and `X-MetaRush-Client: extension` (cross-site forms can't set it), and passes the existing Host allowlist (DNS rebinding). The daemon sends no CORS headers, so a web page can't read any reply. The extension itself keeps its token in its own `chrome.storage.local` and only its service worker (host permission for 127.0.0.1) talks to MetaRush. |
| What it sends | Provenance read from the page is checked: the page address must be a YouTube, TikTok or X video MetaRush recognizes (its canonical address and ID are derived on the server), text is shortened, handles and dates must look right, the channel address must be on the same site. |
| DRM | The extension refuses any video that uses Encrypted Media Extensions (`mediaKeys`); it never tries to capture protected playback. |
| Revocation | **Remove** in Settings → Browser extension (your browsers; an owner anyone's) or `metarush extension revoke <id>` (`--all` yours, `--everyone` for owners) deletes the token at once; the extension's own "Unpair" does the same for itself. |

## Accounts and sign-in ([accounts.md](accounts.md))
Out of the box MetaRush is the owner on their own computer: no sign-in, nobody else gets in. The owner chooses a
sign-in method in Settings → People (email and password, or Tailscale accounts), giving their own sign-in at the same
step; only then can people be invited. The method is stored on the workspace, so every computer agrees.

| Threat | Control |
|---|---|
| Stolen password database | Passwords are argon2id (64 MiB, 3 passes, 2 lanes, 16-byte random salt, PHC string) in `user_credentials`, never in `users`, an answer, a log or the audit; older settings are re-hashed at the next sign-in. |
| Guessable passwords | 12–128 characters after NFKC (any characters), no composition rules or expiry (NIST SP 800-63B); refused when among the ~30,000 most common of that length (embedded list, no network), with fewer than 5 different characters, or containing the person's email name or name. |
| Finding out who has an account | One answer for a wrong email and a wrong password, in the same time (an unknown email verifies against a dummy hash); failures are counted per email whether it has an account or not. |
| Guessing online | After 5 wrong passwords each try waits longer (2^n s, ≤ 15 min); after 10 the email locks for 15 minutes, the owners are notified and the audit records it (`auth_failures`, shared by every computer); 20 tries per minute per address on top. |
| Session fixation and theft | A new session on every sign-in; password sessions last ≤ 30 days and end after 7 unused; `HttpOnly`, `SameSite=Strict`, `Secure` with `__Host-` over HTTPS; a password change or reset, turning an account off or "Sign out everywhere" sets `sessionsValidAfter`, which every computer checks (a session check waits at most 0.75 s for the database, then uses what it read in the last 10 minutes, so playback keeps going through an outage). |
| Passwords in the clear | Typed only on this computer (loopback) or over HTTPS; a plain-http public address refuses them. The CLI reads them hidden from the terminal, never from a flag. Sign-in requests need the dashboard's header (no cross-site form) and same-origin fetch metadata. |
| Invite and reset links | 32 random bytes, stored only as SHA-256, one use (an atomic update), invite 7 days, reset 1 hour, revocable, a new one takes back the old; shown once; a weak password doesn't use the link up. Nothing is emailed. |
| The owner's one-time links | They sign in the owner on this computer only (`/auth` refuses the public address; `dashboard --remote` is retired). |
| Who may manage people | Owners only (`ops.Flags.OwnerOnly`; the host's CLI counts as the owner); the sign-in method changes only on this computer; the last owner can't be turned off, removed or made a member. |
| Who may change this computer's settings | Owners only, enforced on the server for every surface: remote access, the storage move (`/api/storage/choose\|plan\|move` too), the Trash's settings and emptying it, keys, the workspace's voice and generated-video choices and limits, Claude Code's settings, the watched folder (`/api/watch/choose` too) and link-import settings, removing someone else's browser extension pairing (everyone pairs and removes their own), clearing archived projects out for good, the log's settings and deleting entries, the weekly improvement report, this computer's battery setting, machines (the full list is in [accounts.md](accounts.md#what-only-owners-change)). A member is refused on another computer **and** at the host's own address ("Only an owner of this MetaRush can change that.", the owners named in `details.owners`). Every signed-in request carries its person (`ops.OverHTTP`), so an endpoint that calls an op itself and an op that calls another (a Claude Code card a member approves) are held to the same rule; only this computer's own CLI, MCP server and daemon — no HTTP request behind them — count as the owner without an account. Reading stays open to everyone signed in. Tests: `internal/api/owneronly_test.go` (every owner-only op and endpoint as a member from another computer and at the host, the owner by link and by password, the host's CLI, a member's request passed down to another op), `internal/cli` `TestOwnerOnlyOps` (the list), `scripts/accounts-e2e.sh` (a member's view). |
| Tailscale identity | Believed only when Tailscale accounts is the sign-in method; otherwise its headers only keep the spoofing and Funnel refusals below. MetaRush runs without Tailscale; any HTTPS proxy's address works for remote access. |

## Remote access over Tailscale
People on the owner's tailnet open the dashboard from their own computers (setting it up:
[windows.md](windows.md)). MetaRush still listens on 127.0.0.1 only. `tailscale serve` answers at the computer's tailnet name with
HTTPS (a Let's Encrypt certificate Tailscale gets for that name) and hands each request to the dashboard **from
loopback**, keeping the Host the browser asked for, setting `X-Forwarded-Host`, `X-Forwarded-Proto: https` and
`X-Forwarded-For` (the browser's tailnet address), removing any `Tailscale-*` header the browser sent, and adding
`Tailscale-User-Login` / `-Name` / `-Profile-Pic` for people (never for tagged computers or Funnel). That is the only
way in: nothing listens on the tailnet interface. Threats: a browser or program pretending to be someone it isn't,
a request that didn't come through serve, a hostile page (DNS rebinding, CSRF), a stolen cookie, a lost device, and
a person who should no longer get in.

| Threat | Control |
|---|---|
| Spoofed identity headers | `Tailscale-*` headers are believed only on a request that came from loopback **and** names the public address (`dashboard.publicURL`) in its Host, which is how serve connects. Any request carrying a `Tailscale-*` header (`-User-Login`, `-App-Capabilities`, anything) on this computer's own address, or from anywhere but loopback, is refused (403, "MetaRush turned this visit away"). An identity also counts only when `X-Forwarded-For` is a Tailscale address (100.64.0.0/10, fd7a:115c:a1e0::/48). Header values are read the way serve writes them (RFC 2047 "Q" words for letters outside ASCII); control characters are dropped. |
| Requests not from loopback | The public Host is refused unless the connection came from loopback (a dashboard bound elsewhere stays Host-checked as before, and still never believes Tailscale headers). Tested on a real socket from fe80::1%lo0, an address on this computer that isn't loopback. |
| The public internet | Tailscale Funnel requests (`Tailscale-Funnel-Request`) are refused; `doctor` and `remote status` fail when Funnel is on for the address. |
| DNS rebinding | The Host allowlist is unchanged: 127.0.0.1, localhost, [::1] and the dev origins, plus exactly the public name (and its default port) from loopback. A page that rebinds its own name to 127.0.0.1 or to the tailnet address still sends its own Host and is refused; a page can't send the tailnet name as Host, and its TLS connection to the tailnet address fails the name check. |
| Who signs in | The sign-in method (above). With **Tailscale accounts**, `dashboard.tailscaleLogins` lists the accounts that are signed in by themselves; an account not on the list gets a plain page that says how the owner adds them, and no person is made for it; adding people works only at the computer that runs MetaRush (a session from elsewhere can narrow the list, never widen it, `remote enable` included). With **email and password** Tailscale's identity headers are ignored and people sign in with their accounts. One-time links (`metarush dashboard`) sign in only the owner, on this computer. Every change is people-only (HumanOnly; the CLI asks at an interactive terminal), owner-only and audited. |
| Attribution | Each account is a person in the workspace (`usr_…`, made on the first sign-in with Tailscale's display name; an existing person with that email, or the one this computer's own Tailscale account was linked to by `remote enable`, is reused). The audit trail, the activity log, "Approved by", notifications, uploads, the extension's sends and Claude Code conversations are theirs; in a conversation several people share, each message, card and decision is the person's who sent or made it. Approval stays HumanOnly and counts for any signed-in person. Sign-ins are audited (`remote.signin`, with the tailnet address). |
| Cookie scope | Over HTTPS the session cookie is `__Host-mr_session`: Secure, HttpOnly, SameSite=Strict, Path=/, no Domain, so another computer on the same tailnet (same site under `ts.net`) can't set or read it. `X-Forwarded-Proto` is believed only on the public address. A session is good only where it was made (public or this computer's own address), and a Tailscale session only with the same account in the header on every request: a copied cookie is nothing on another computer, another account or a tagged computer. |
| CSRF | Unchanged: changes need `X-MetaRush-Client` (a cross-site page can't set it without CORS, which MetaRush never answers) and the cookie is SameSite=Strict. Because the tailnet identity rides along with every request like a cookie, a Tailscale account is signed in by itself only on a same-origin or typed-in request (`Sec-Fetch-Site`), never on a cross-site one. |
| A lost device | Remove it from the tailnet in the Tailscale admin console (nothing reaches MetaRush without it), then `metarush remote signout --all` (or Settings → People → Remote access → Sign out other computers) ends every session made through the public address; this computer's own browser stays signed in. |
| Revoking a person | `metarush remote remove <account>` (or Remove in Settings, also from another computer) takes them off the list: their next request is refused (a change made in a terminal is read from config.yaml on the very next request) and their sessions are deleted at once; a live event stream they have open ends within 10 seconds. `remote disable` clears the address and the list, signs every remote browser out, and says how to stop serve (`tailscale serve --https=443 off`); until serve is stopped, its visits are refused because the public name is no longer accepted. |
| Host-only actions | The native folder picker would open on the host's screen, so it is refused from another computer (the dashboard browses folders instead); Show in Finder and the like say "on <machine>"; downloads (renders, resources, an editing-app export as a .zip, the extension) come to the browser. |
| Changing Tailscale | MetaRush only reads `tailscale status --json` and `tailscale serve status --json`. It runs `tailscale serve --bg <port>` or `--https=443 off` only for `remote enable|disable --apply`, after a plain yes at an interactive terminal, and never when HTTPS certificates are off (serve would stop and wait for a browser). The browser can't run them. Under `go test` the real `tailscale` never runs (tests use `internal/testutil/faketailscale`). |
| Tests | `internal/api/remote_test.go` (the whole handler stack: allowed and unlisted accounts, spoofed headers on the local address, from a non-loopback socket and from a non-tailnet address, Funnel, rebinding, cross-site, CSRF, cookie names and flags, revoking, a copied cookie, link sign-in over HTTPS and HTTP, attribution, approvals, the extension and downloads, a change in config.yaml applying on the next request, an open stream ending after revocation), `internal/remote` (status and serve parsing, the ops, people), `internal/config`, `internal/sessions`, and `scripts/remote-e2e.sh` (Playwright through an HTTPS stand-in for serve: sign-in, refusal pages, spoofing from a non-loopback hop, the microphone over HTTPS, the "on <machine>" labels). |

Residual risks: MetaRush trusts loopback, as Tailscale recommends for its identity headers, so **any program on the
computer that runs MetaRush can claim to be a listed account** by connecting to 127.0.0.1 with the public Host and
the headers. A program running as the owner could already do anything MetaRush can (it can read the same keychain
and settings); the new exposure is other macOS or Linux accounts on that computer. Don't list Tailscale accounts on
a computer where people you don't trust have accounts of their own; use sign-in links there instead. Anyone the
owner lets onto the tailnet can reach the address and, with a link or a listed account, everything the dashboard
offers. The tailnet admin console is part of the security boundary: whoever can add devices or change ACLs there
decides who can reach the address.

## Per-machine credentials
`metarush machine invite` gives each machine its own object-store key and (on Atlas) its own database user
(`readWrite` on the MetaRush database only, limited to the cluster). Tigris keys are minted with scope
`no_default_allow` (no bucket listing/creation, no key or policy creation) and limited to the workspace's store
prefix by an IAM policy (or a `ReadWrite` bucket role with `--key-scope bucket`). Secrets travel only inside a 0600
join bundle that is never overwritten and never printed; the database password reaches the Atlas CLI on stdin, not
argv. The CI key (`machine ci-key`) can only touch `<bucket>/ci-test/*`. See
[runbook-add-machine.md](runbook-add-machine.md).

`metarush machine rekey` gives a machine that joined before this its own key in place: people only, on that
machine only; `--dry-run` calls nothing. The new secret is never printed or audited: it goes straight to a new
keychain entry (or `<home>/.env`, 0600), is registered with the activity log's redaction, and is tested before and
after `config.yaml` switches; environment variables that would override the key are refused first. Any failure puts
`config.yaml` back byte for byte, restores the keychain or `.env` and deletes the new key. This computer's keychain
copy of the old secret is removed; the old key itself is deleted by a person (once no machine uses it), never by
MetaRush, since a CI job or a script outside MetaRush may still use it.

## Moving the media from the dashboard
Settings → Storage moves the media with the same `storage.plan` / `storage.migrate` as the terminal.
Both stay `LocalOnly` (and `storage.migrate` `HumanOnly`): `/api/ops` refuses them, and the dashboard gets three
narrow endpoints instead.

| Area | Control |
|---|---|
| Endpoints | `POST /api/storage/{choose,plan,move}`: signed-in session, `X-MetaRush-Client` CSRF header, Host allowlist, strict JSON bodies (unknown fields refused, 16 KB). The browser never names a file: it sends a form, and the daemon writes the storage description itself in `<home>/state/storage-move/dashboard/<id>.yaml` (0600, ID from 96 random bits). |
| Typed text | Taken as written: a storage description expands `${VARIABLE}` and reads `keychain:<name>`, so any field with `${`, line breaks or NUL, and an access key ID that names a keychain entry, are refused (otherwise a form could read this computer's secrets into a name the page shows, or send them to a storage it names). Addresses must be `http(s)` without credentials; a folder must be a full path; a GCS key file a regular `.json` file of at most 64 KB. |
| The secret key | Sent once in the body of `/api/storage/plan`, never returned (responses carry names and locators only) and registered with the activity log's redaction (`logbook.RememberSecret`). Keychain installations keep it in the keychain under `s3-secret-access-key-<id>` and the description names the reference; env installations refuse a typed secret and take the name of a variable already in the environment file instead. The page keeps it only in component state and clears it once the move starts. |
| The move | Runs as `metarush storage migrate --dashboard-move <id>` in a process and session of its own (`tools.Start`: the allowlisted MetaRush binary itself, no shell), so it keeps going while the daemon restarts with the new storage, and its output goes to a 0600 log next to the description. Confirming in the dashboard writes a one-time grant: 32 random bytes handed to that process on its stdin (never in argv), of which only the SHA-256 is kept; the process must present it within two minutes, it is compared in constant time, and a claim file (`O_EXCL`) makes any first attempt, right or wrong, the last. In assistant mode (`METARUSH_VIA=assistant`) the process refuses outright, before the read-only allowlist would. One move at a time per machine (the move's lock, the job and the grant are all checked). |
| Nothing deleted | Only `storage.migrate` touches the media: it reads the old storage, never overwrites differing files in the new one and never deletes. The dashboard's own bookkeeping is the description and record of each move; plans nobody confirmed within a day are forgotten. |
| Other machines | `storage.status` (read-only) compares this machine's storage with the workspace's record and offers the new storage as a form with provider, bucket, folder and address only, never a key: each machine switches with its own keys. |
| Tests | `internal/ops/storage_dashboard_test.go` (descriptions keep references only, refused forms leave nothing, grants: unknown, twice, wrong token, old, used), `internal/api/storage_test.go` (session and CSRF, the secret never in a response, the grant on stdin and not in argv, one move at a time), `internal/cli/storage_test.go` (the moving process with and without its grant, in assistant mode), `scripts/storage-e2e.sh` (two installations in a real browser; the old folder keeps every file). |

## Local model servers
The transcription model servers (`transcribe-model-server`) talk to the worker over pipes. whisper.cpp's is
`whisper-server`, an HTTP server, so it is fenced: it listens on 127.0.0.1 only, on a free port, and answers only
under a random 128-bit path (whisper-server sends `Access-Control-Allow-Origin: *`, so without it any web page could
use it, including its `/load` endpoint, which loads a model file from a path it is given); it serves no files but a
private one whose random word proves, before each clip, that the program answering is MetaRush's own (another
account can't stand in for it and receive the audio if it lost its port); it runs in the model server's process
group and stops with it. Residual risk: other accounts on the same computer can read the random path in the process
list (it is an argument) and so could use the server or ask it to load another file while it runs (at most 10 idle
minutes after the last clip). On a computer shared with accounts you don't trust, turn it off with
`transcription.resident: false` (whisper-cli then runs once per clip, with nothing listening).
## Project motion graphics
A project can carry its own Remotion components (`motion/<name>/`, [motion-graphics-as-code.md](motion-graphics-as-code.md)).
Threats: a buggy or malicious component, written by a model or a collaborator, trying to read local files, send
data out, spend the machine's time, or act as the person in the dashboard.

| Area | Control |
|---|---|
| Identity | A component is the SHA-256 of a canonical archive of its sources (Go builds it: sorted paths, LF, UTF-8, `.tsx`/`.ts`/`.json` only, no links, packages, `tsconfig.json` or media). The archive is stored at `objects/<sha>`; the renderer refuses an archive whose bytes don't hash to the version the plan names. Editing one character makes a new version. |
| Imports | Parsed with the TypeScript compiler before anything is bundled (in every check and again in every render): only `remotion`, `react`, `zod`, `@remotion/zod-types`, `@remotion/shapes`, `@remotion/paths`, `@remotion/layout-utils`, `@remotion/transitions`, `@metarush/motion` and the component's own files. `import()`, `require`, `eval`, `new Function`, `.constructor(…)`, string timers, Node built-ins, URLs, reference directives, network APIs, workers and WebAssembly are refused with file and line. The esbuild resolver enforces the allowlist a second time; components cannot supply loaders, plugins, packages or build settings. |
| Where it runs | Only in the headless browser page Remotion renders; Node treats the source as text and the bundle as an opaque file served from loopback. The dashboard shows frames, a contact sheet and a preview video (served with a sandboxing CSP) and the source as text — never live code; its cut preview draws a placeholder. |
| Network | Every render page (templates too) is jailed: a refusing proxy that records the host tried, a bypass list with only the render's own loopback servers, host-resolver rules that make every other name unresolvable, WebRTC limited to the proxy, a CSP without eval, and a Node-side guard on the downloads Remotion makes for the page. With a motion graphic in the plan, nothing renders unless the jail was applied. A check whose component tries the network fails and names what it tried. |
| Limits | Per-frame time limit, total time limit (checks 240 s; renders 600 s + 20 × the cut's length, then Go kills the process group), 2 MB bundle limit; Chrome processes are killed with their renderer. |
| Approval | `motion approve` (and `--reject`) and `motion revoke` are `HumanOnly`: the dashboard, or an interactive terminal with a typed confirmation; refused on the assistant channel and in non-interactive shells. Decisions are compare-and-swap, recorded with who, when and a note, and audited (`motion.check`, `motion.approve`, `motion.reject`, `motion.revoke`). Workers refuse to render, and QA to check, any revision that uses a version that is not approved; `edit check`/`cut check` report it. From the dashboard, `motion.check` only accepts folders inside the assistant's conversation proposals. |
| Tests | Forbidden imports refused (`fs`, `child_process`, dynamic import, `eval`, `new Function`, `require`, and more) in `npm run test:motion -w video` and in Go; the render self-test's `motion-security` variant shows an obfuscated `fetch`, an image and an IP literal reach nothing (a loopback sink sees no request), Node won't fetch audio the page names, a stuck component is stopped and its browser killed, the total time and bundle limits stop renders, and forbidden imports or mismatched archives never render; Go tests cover the worker refusing unapproved and withdrawn versions, one character making a new version that waits for approval, and revoke. |

Residual risks: a component a person approved can still look wrong (QA and review copies catch it as for any
cut); an obfuscated name computed at run time gets past the static scan but not the jail; `motion studio` runs a
component in the author's own browser, outside the jail, for components they wrote or read.

## Remotion sources
A project can keep a whole Remotion project as a source ([remotion-sources.md](remotion-sources.md)): code
written by anyone (a folder on this computer or a GitHub repository), its own package versions and its `public/`
files. Threats: code that tries to run on this machine (install scripts, `remotion.config.ts`, webpack plugins, npm
scripts), reach the network or this computer while it renders, read or leak secrets, steer Claude with instructions
in its files, or reach a cut without a person seeing it; a malicious package version; a project that fills the disk.

| Area | Control |
|---|---|
| The original | A folder is only read: files are hashed and uploaded, git answers read-only questions (`--no-optional-locks`, no `status`), nothing is written into it. A GitHub repository is fetched with the git runner (fresh bare repository, hooks, filters, other protocols, prompts and LFS off, blobs read raw, the person's own sign-in; addresses with credentials are refused). |
| What comes in | `.env*`, keys, certificates, `.npmrc`, credentials and any file whose contents look like a secret (API keys, private keys) are never copied; neither are `node_modules`, `.git`, build caches, `out/` (its videos come in as footage), links, odd names and coding-assistant or tool settings (`.claude/`, `CLAUDE.md`, `AGENTS.md`, `.cursor*`, `.github/`, `.vscode/`, `.husky/`), so a checkout Claude edits carries no other project's instructions or hooks. Per-file and per-project size limits; every left-out file is listed with its reason. |
| Packages | Installed once per lockfile into `<home>/remotion/envs/<key>` with `npm ci --ignore-scripts` (also `npm_config_ignore_scripts`) from the public npm registry only, from an env `package.json` that carries only dependency fields (the project's scripts never reach npm). Lockfiles with another registry, a missing integrity hash, or git, file or link dependencies are refused before anything is installed. A version whose packages differ from what people allowed stops at its check until a person allows that lockfile (`remotion allow`, HumanOnly); the import's set is allowed by the person importing it. |
| Node code | The project's Node code never runs — except the steps of a refresh a person starts (below): no npm scripts, no `remotion.config.ts` (read as text; literal format, quality, entry point and delay settings applied), no webpack override, no inline loaders or remote imports (refused by the static read, `analyze.mjs`, which parses with the TypeScript compiler and evaluates nothing). What runs in Node is MetaRush's `run.mjs` and the pinned `@remotion/bundler`/`@remotion/renderer`, which must match `remotion`'s version. |
| Where project code runs | Only in the jailed headless browser: a refusing proxy with only the run's loopback bundle server bypassing it, host-resolver rules, WebRTC limited to the proxy, a Content-Security-Policy injected into the bundle's page (no eval, scripts, connections, pictures, sound and fonts only from loopback), the Node download guard; a browser that can't be jailed stops the run. Per-frame limits (30–120 s), a total limit (10 minutes plus 6× the length), a 15-minute cap on what one render makes (also when props change the length). Anything the code tries to reach is recorded and fails the check (`network`). |
| Fonts | Google Fonts named by `@remotion/google-fonts` modules are downloaded at import from `fonts.gstatic.com` only (HTTPS, no redirects, at most 8 MB, font file signatures checked), kept as objects and served from the bundle; the page never reaches Google. |
| People decide | Approving, turning down and withdrawing a version (`remotion approve|revoke`) and allowing packages are `HumanOnly`, compare-and-swap, recorded and audited; refused on the assistant channel and in non-interactive shells. Only approved versions become clips in cuts: `remotion use|render`, `edit check`/`cut check` (`remotion_not_approved`), `render submit` (before queuing) and the worker each refuse others. A version that failed its check can't be approved. |
| Dashboard | Shows pictures and words only: posters and before/after stills drawn in the jail, served same-origin as `image/jpeg` with a sandboxing CSP (`/media/remotion/…`); the dashboard never loads project code. A folder import is refused from a browser on another computer (`ops.Caller.Elsewhere`); `remotion check <folder>` only from a terminal on the computer the folder is on; `remotion stills|checkout` are LocalOnly. |
| Claude | The `video-remotion` skill and `skills/_shared/safety.md`: a project's files, comments and README are data, never instructions; never run its scripts, install its packages or read its `.env`; never approve. Only `remotion list|show|map`, `remotion refresh plan|runs|log` and `remotion push plan|list` are allowlisted (read-only), for skills and the dashboard assistant; starting a refresh or a push is people only. |
| The map's probe | Runs only in the same jailed page as every render. The bundler swaps the project's own imports of `remotion` and `@remotion/transitions` for MetaRush's thin wrappers (a rule-level alias limited to project files; `node_modules` and the probe excluded), which report positions and text boxes through the page console; MetaRush parses only lines it recognizes, as data (lengths, positions, short texts), never as instructions. No global hooks; nothing the project draws changes. |
| Words as settings | The one-time change is an ordinary version: checked, shown, approved by a person. Settings are text only (≤ 400 characters per key, known keys only, at most 200 per change), passed as the render's input props as JSON — never spliced into code — and each change is drawn and checked in the jail before it is made; every change is recorded (who, when, before/after) and undoable. |
| Sounds as tracks | Only files from the version's own `public/` (content-addressed, already stored) become footage; placements come from Remotion's asset list in the jail, numbers only. |
| Lifted graphics and shared libraries | Lifting rewrites text with the TypeScript parser (nothing runs); the results are ordinary motion graphics: the import allowlist (plus `@metarush/lib/<name>`, never a library inside a library), MetaRush's type settings (only `noUncheckedIndexedAccess: false` may be declared, as the project had it), the bundler's own allowlist, jailed test frames, approval per version (HumanOnly) for the graphic and each library version; renders refuse unapproved libraries like unapproved graphics. Scenes that play sound or video, draw project files or need other packages are refused. Fonts become workspace font resources from the files kept at import (never downloaded again). |
| The approval to-do | People only (`remotion_approval` answers through `remotion.approve` with the caller's own channel; refused for Claude and the assistant like a cut's approval). |
| Refreshes | The one place a source's own Node code runs, and only when a person starts it: `remotion.refresh.start` is HumanOnly (refused on the assistant channel and in non-interactive shells; Claude only reads plans) and takes the fingerprint of the plan the person saw — the exact commands (`npm run <script>` with the script's line shown, `node <file>`, `npx --no <tool>`: typed arguments, no shell line built by MetaRush, no downloads), the keys and their variable names (names that steer programs — `PATH`, `HOME`, `NODE_*`, `DYLD_*`, `LD_*`, `npm_config_*`, `METARUSH_*`, proxies… — refused), the outputs, the hosts its code names and the machine. The job is pinned to that machine (its keys) and never retried: a run cut short is reported, not run again. Each step gets a fresh copy of the version in the system's temporary folder (real copies, never links into MetaRush's cache; packages an APFS clone of the package environment, or mounted read-only on Linux), an environment built from nothing (Node's `PATH`, a fresh `HOME`/`TMPDIR`, a per-source npm and browser cache, `CI=1`, the picked keys — no database address, storage keys, SSH agent or MetaRush home) and the operating system's sandbox: on macOS `sandbox-exec` with a profile written per run (reading and writing denied in MetaRush's home, cache, scratch and media folders, the person's home folder except Node.js's installation, and the original folder; writes only in its room and cache; the keychain's services unreachable), on Linux bubblewrap (the system read-only, the home and MetaRush folders replaced by empty ones, the session bus hidden). A computer that offers neither refuses refreshes. Limits: 30 minutes a step, 2 hours a refresh. What the steps printed is kept with the keys passed, MetaRush's configured secrets and credential shapes hidden. Only changes inside the declared outputs, under the import's rules (secret names and contents, packages, git, caches, sizes), become a version — checked in the jail like any and approved by a person. |
| Pushing back | HumanOnly with the plan's fingerprint (the changes, the target, the branch); a job pinned to the asking machine uses the person's own git and gh sign-in and stores nothing. git runs with hooks, prompts and protocols other than https, ssh (batch mode) and — for a repository on this computer — local paths off, on a fresh bare repository that fetches the original commit (depth 1); the commit is written with git plumbing (`read-tree`, `hash-object --no-filters`, `update-index --index-info`, `write-tree`, `commit-tree`, signing off), so nothing of the repository's own runs and files the import left out stay as they were. The push is a plain `git push` of one new ref: never `--force`, never the remote's HEAD, `main` or `master`, never a branch MetaRush didn't make, and a later version moves MetaRush's own branch only as a fast-forward of its last push (a branch someone else changed is refused). Remote addresses with a password in them are refused. The pull request is `gh pr create` into the default branch. The words helper is unwrapped by MetaRush's parser (nothing runs). |
| Tests | Go tests: secret names and contents, `.gitignore`, assistant and tool files left out, lockfile refusals, decisions, renders refused from unapproved and withdrawn versions; `node video/render/source/test.mjs`: the static read refuses inline loaders, remote and dynamic imports and runs no project code; the acceptance step: a fixture whose postinstall exits 42 imports and renders (its scripts never ran), `.env` and assistant files left out, the folder unchanged, a change that fetches from the internet fails its check (`network`), approval only as a person, withdrawal refuses a new render. |

Residual risks: a malicious package version that the lockfile pins from the public registry runs in Node while
bundling and rendering, like in any npm project (registry and integrity are pinned, the package set is shown and
changes need a person); a Chrome sandbox escape from page code; a project that renders something other than its
source suggests (people review stills before approving and renders like any footage); a secret in a file whose name
and contents look harmless is copied. A refresh a person started can reach any public host (only this computer's services — loopback,
MetaRush's ports, the database's socket — are closed to it; the plan lists the hosts its code names), read files outside the home folders (system folders, other disks) and
spend the keys it was given; an escape from the operating system's sandbox would reach the person's account. A push
writes to the repository the person can write to, as a branch they review.

## Abilities ([abilities.md](abilities.md))

An ability is code MetaRush didn't write, so it gets less than anything else that runs:

| Area | Control |
|---|---|
| What runs | Only a version an owner approved (`ability.approve`: OwnerOnly and HumanOnly, refused to Claude on every channel) after reading what it installs, what it reaches, its keys and their hosts, what leaves, its cost and licence. The version is the SHA-256 of a canonical archive; the stored archive is checked against it before every run; links, installed packages and credential shapes are refused at the check. Every version ran once at its check, in the sandbox with the network off. |
| Programs | Only programs a person set up on that computer, pinned by path and SHA-256; a changed program is refused until a person sets it up again. No shell; no code on the command line (`python3 -c`, `node -e`). |
| Files | A room of its own in the system's temporary folder (its files read-only, its inputs; it writes only its output, home and temporary folders), an environment built from nothing; macOS `sandbox-exec` denies everything but the system, the program with its own installation (never a folder of programs like `~/bin`) and the room — MetaRush's home, cache, scratch and media and the person's home are denied last, so they always win, and a read that is or holds one is refused; metadata only there and above; the keychain, clipboard, `/dev/tty` and other services unreachable; bubblewrap on Linux mounts only those. Where neither works, MetaRush refuses, in plain words. |
| Network | Off unless declared. Declared hosts are reached only through a proxy started for the run: HTTP(S) to those names only (never this computer or a local network, even by a name that points there), a password of its own, headers capped at 32 KB, at most 10,000 requests and the run's byte limit; an ability that says it sends only words has one outbound budget for the run (request lines, headers and bodies: 256 KB) and at most 200 requests. An open network (`network: open`) is a separate agreement an owner gives at approval: any public host, still through the proxy (never this computer or a local network, and never listening where anyone can reach it: on Linux a program may listen only inside its sandbox's own network), and such an ability can't use keys. |
| Keys | Kept in the keychain (or the home's `.env`), added only by an owner. The code reads a random stand-in; the proxy puts the key only in the one place its manifest names (a header or a query parameter), only on requests to that key's hosts and only over HTTPS, and refuses the stand-in anywhere else. Answers are opened (gzip, deflate; other compressions refused) and the key is taken out in every written form (raw, URL- and JSON-escaped, base64); the log, the outputs (one holding a key is left out) and `result.json` the same. A key named after one of MetaRush's own integrations goes only to that service. |
| What comes back | Only regular files of the kinds it declared, within its limit, copied out of the room without following a link (only the copies are taken in), through the same classifier as a file you add, each with how it was made (`madeWith`); everything else is left out with the reason. |
| Processes | The program starts in a session of its own (no terminal); when it ends, is stopped or runs out of time, everything it left running is killed (`tools.Spec.Contained`; Remotion refreshes too). |
| Who starts it | A free run that uses no key and sends nothing but words: anyone, Claude included. With a key: a person each time, whatever the manifest says it costs. Priced: a person, agreeing to the estimate. Pictures, sound or footage leaving, something outside MetaRush changing, or the whole network: a person each time. A likeness: not yet. Runs are jobs pinned to the computer that asked, never retried. |

## Dashboard assistant (local Claude Code)
The Claude Code panel holds conversations with the person's own Claude Code on the daemon's machine; MetaRush makes
no model calls and holds no Anthropic credentials. Threats: prompt injection through anything the model reads
(transcripts, captions, filenames, comments), a hostile web page driving the local dashboard, and a model trying to
change state or read secrets.

| Area | Control |
|---|---|
| Messages | Signed-in session cookie + `X-MetaRush-Client` on POST (CSRF) + Host allowlist (rebinding), like every endpoint. Message ≤ 8,000 characters, at most 10 queued; project/revision/asset/clip context is sent as IDs, validated and resolved to names on the server. Live CLI commands (`assistant ask/continue/…`) go to the local daemon with a one-time sign-in nonce (as `metarush dashboard` does) and `X-MetaRush-Client: cli`. |
| Process | One long-lived Claude Code process per conversation, spawned through `internal/tools` (allowlisted binary, argv only, never a shell). Messages are written to its stdin as stream-json, never placed in argv. Clean environment: PATH with the shim first, HOME/locale/proxy settings, Claude Code's own auth variables and the daemon's `METARUSH_*` settings, never one that carries a secret (`secretpath.IsSecretEnvName`: database addresses, keys, tokens, passwords; the shim's metarush reads those from the home itself) — nothing else. Every spawn, including every `--resume`, re-applies the same locked-down flags: `--permission-mode dontAsk`, `--tools`, `--allowedTools`/`--disallowedTools`, `--strict-mcp-config` (no MCP servers), `--setting-sources project,local` (no user settings, no personal skills), the appended system rules, `--max-budget-usd` (what is left of the conversation's limit), `--max-turns` (steps per message). Per-message timeout; Stop sends Claude Code's interrupt, then SIGINT, then kills the process group; idle processes are ended after `assistant.idleMinutes`. |
| Permissions | `dontAsk`: anything not pre-approved is denied. Bash only for `internal/assistant.ReadOnlyCommands` (the interactive read-only allowlist without `schema export` and without the assistant's own commands). Reads: the workspace (working directory), the scratch folder (frames, contact sheets), the media cache (precomputed contact sheets, content-addressed) and the conversation's proposals; a scratch or cache folder configured as (or above) the installation home is left out, so `config.yaml` and `.env` stay unreadable. Writes: only the conversation's `proposals/` folder. Explicit denies for mutating commands, `metarush assistant`, `--out`, `--home`, WebFetch, WebSearch. The workspace carries the skills with their `allowed-tools` removed and no settings file: before every launch (and resume) MetaRush deletes any `.claude/settings.json`, `.claude/settings.local.json`, `CLAUDE.local.md` or `.mcp.json` there, since project and local settings would otherwise be loaded. A real run showed a model trying to write such a file to grant itself Bash after a refusal; the write was denied, and the system rules now say a refusal is expected. Verified with Claude Code 2.1: reads of the installation's `.env`/`config.yaml` and of `/etc` are denied, including through auto-approved shell builtins. |
| Shim | Claude runs MetaRush as `metarush` through a shim in a folder of its own, `<home>/assistant/shim` (0700), next to its working folder and never inside it or any folder it may write: it reaches the shim only through PATH, where it comes first. The allowlist names commands, so a run by path is refused; in the working folder there is nothing to find and run that way (an earlier layout kept the shim in `workspace/bin`, where Claude found it and ran it by its path; that folder is removed). Claude cannot change it: no rule allows writing there, an explicit deny forbids every edit of that folder (deny beats allow, a settings file included), and every launch and resume writes it again as a plain file in a plain folder, replacing a changed copy, a link left in its place (never writing through it) or a link in place of the folder. Tests: `TestShimIsReachedOnlyThroughPath` (an upgraded installation loses the old copy; PATH resolves `metarush` to the shim; no allow rule covers it; the deny is there and the others are kept) and `TestShimIsRestoredBeforeEveryLaunch`. |
| Defense in depth | The shim sets `METARUSH_VIA=assistant` and pins the installation home. The CLI then refuses every command outside the read-only list, any `--out`/`--dir` and any other `--home`; the ops layer refuses every mutating or human-only op on the `assistant` channel. A misconfigured or bypassed Claude Code still cannot change shared state through MetaRush. |
| Changes | Claude never makes them. Plans are files the server re-checks with `edit.check` against the current head whenever they are shown; it sets `origin` itself. A change Claude asks for (a refused command) becomes an action card whose operation and input the server builds from Claude's command (known commands only; plans must be this conversation's proposals) — never from the browser. A diagram card's Mermaid or D2 is read only from this conversation's proposals folder (no links out of it, at most 50,000 characters) and its boxes are listed on the card; a repository or page card refuses this computer and the local network like the CLI. Conversation and sound cards are previewed with nothing saved, made or spent (no version, no decision, no processed or paid voice, no music linked, no beats analysed); a cloud clearer-voice card is priced first and can't be confirmed over the project's budget, the plan's credits or without this computer's key; studio quality's people-only setup runs only from a card the person confirms in a styled dialog, and never beside a setup already running. A person runs it with `assistant.act` (human-only, refused on the assistant channel) as themselves on the human channel, after a styled confirm for decisions such as approving; from the CLI, `assistant apply` needs the plan's confirm token and `assistant act` asks in the terminal. Claude is told the outcome as its next message. Revisions keep `origin = assistant:<conversation>/<t<turn>/<file>>`; conversations, messages, settings and cards are audited (`assistant.ask`, `assistant.turn`, `assistant.configure`, `assistant.settings`, `assistant.action`). |
| Images | `GET /api/assistant/image?root=…&path=…` serves only images Claude looked at under the scratch, cache or assistant folders: clean relative paths, no traversal (also not through symlinks), regular files ≤ 25 MB whose content sniffs as JPEG/PNG/WebP/GIF. |
| Sessions and data | Claude Code keeps each conversation's session (its full transcript, including what it read) in its own data folder, `~/.claude/projects/<encoded assistant workspace path>/<session id>.jsonl`, which `--resume` needs; archiving a conversation does not delete it, and `/fresh` starts a new one. Only the machine holding that file can continue the conversation. MetaRush keeps the raw stream in `<home>/assistant/conversations/<id>/stream.jsonl` (0600) and a bounded, condensed transcript in MongoDB (`assistant_conversations`), which every machine of the workspace can read: a project's conversations list for everyone working in the workspace, the workspace-wide list the person's own by default, and anyone signed in can open or continue any of them (each message, card and decision recorded as its person's). |
| Billing | The panel says whether Claude Code bills a Claude plan or an API key. A conversation's limit is tokens; on a plan there is no dollar cap and the plan's own usage is shown, with an API key the dollar cap stays (`--max-budget-usd`, real spend). |
| Usage and memory | MetaRush may send Claude Code's own `/compact` (with fixed instructions) as a turn of its own and starts it with `--autocompact` and `CLAUDE_CODE_PROMPT_CACHE_TTL=1h`; neither widens what Claude may do. Claude may run a helper (the Task tool): it runs under the same `--tools`, allow and deny rules and `dontAsk`, and its Bash calls go through the same shim. |

Residual risks: what the model reads (including transcript text) goes to Anthropic under the person's Claude Code
account — the same as using Claude Code in a terminal — and stays in Claude Code's session files on that machine.
When the daemon was started with `METARUSH_*` environment overrides, the Claude Code process inherits the settings
among them so the shim resolves the same installation, but never a secret (a database address, a key, a token): the
shim's metarush reads those from the home (keychain or `<home>/.env`), so a daemon whose database address came only
from its own environment leaves the shim without one.
A person can still apply a valid but unwanted change from a card; the plain summary, the diff and warnings under
Details, and immutable revisions are the mitigation. Conversation transcripts in the database may contain transcript
excerpts and are visible to every member of the workspace who lists all conversations.

## Lost laptop
`metarush machine revoke <name> --atlas` on an admin machine: deletes its storage key (access stops immediately) and
database user, marks the installation revoked (init and doctor refuse it) and audits it. Machines that joined before
per-machine keys share a key with others; give those their own keys first (`machine rekey` on each; `machine list` flags shared keys). Its
local cache holds copies of media it worked on — treat the device as exposed.
